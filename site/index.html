What the logs showed

Five things that decide whether a pacing drone is right on the clock, found by flying and measuring, not assumed.

1

Position-only setpoints: lap times look right, the drone is a second late

Streaming only positions to PX4 gave laps within — ms of 59 s. Yet the drone crossed the line — s late every lap, — m behind the runner it was meant to pace. PX4's position loop turns position error into velocity, so in steady flight the drone trails by speed ÷ gain.

lag ≈ v / MPC_XY_P = 6.78 / 0.95 ≈ 7.1 m (≈ 1.05 s)

A lap-time readout alone would never show this. The fix is to send velocity and acceleration with every position, which this pacer does (pos + vel + acc, 50 Hz).

2

A waypoint mission can't hold a pace through the bends

The same oval as a PX4 mission (QGroundControl-style): 71 fly-through waypoints, every 7.2 m on the bends, mission speed 6.78 m/s, PX4 defaults. Laps came out at — against 59 s. Bends averaged — m/s and straights — m/s. Mission mode plans each waypoint's speed for the corner it turns, and it has no time target.

Missions are fine for "fly the oval" (Phase 1 item 3). For programmable lap times, timing has to be in the setpoint stream, which is how this is built.

offboard pacerwaypoint mission
3

Drag belongs in the feed-forward. Measure it from a log, don't guess it

With velocity and acceleration but no drag term, the drone ran — m wide on the bends and — m behind the runner. PX4's velocity integrator has to find the tilt that cancels drag. As the velocity vector turns through each bend, the integrator lags it.

a_ff = a_path + c·v, c identified by least squares from any flight log: a = f_thrust − c·v

PX4's SIH quadcopter has linear drag 1.0 N/(m/s) on 1.0 kg, so c = 1.00. From the no-drag run, the identifier recovered 1.008 using only the EKF estimate (what a real flight log offers) and 1.000 from simulator truth. In Gazebo the same procedure gave — for the x500 from its calibration lap, and that value flew the paced laps.

A GPS-delay mismatch hides inside perfect lap times

The first Gazebo run had laps within — ms of 59 s, yet every line crossing was — ms late. The cause was in the estimator: PX4's default EKF2_GPS_DELAY is 110 ms, Gazebo's simulated GPS has none, and the EKF placed the drone — m (— ms) ahead of where it really was. The controller flew that estimate onto the pace, so the drone itself trailed.

Set to 0 for Gazebo (in config/gazebo_59.toml), the estimate-to-truth offset fell to — ms and the worst crossing to ±— ms. On a real drone the same setting has to match the receiver's actual latency; a wrong value shows up only as a constant offset to the pace clock.

5

Time comes from the autopilot, not the script

The setpoint for "now" is computed from PX4's own clock, read from ODOMETRY timestamps through a sliding-minimum offset filter. A late tick from the companion script sends the correct position for the real time; it never replays a stale queue. Setpoints went out every — ms on average, with a worst gap of — ms, against PX4's 1000 ms offboard-loss failsafe (COM_OF_LOSS_T). Offboard mode never dropped in any run.

Height: SIH's baro-based height wandered — m RMS from truth at a 3 m target. For real flights near athletes, a downward rangefinder or RTK GPS height is the obvious next step.

Pace planner

A first cut of the "simple interface for target lap times". Enter splits and it builds the same schedule the pacer flies, using the same maths as trackpace/schedule.py. It checks the plan against PX4's speed and tilt limits and writes the config file.

Run it yourself

  
Ubuntu 22.04 or 24.04 (or WSL2 on Windows). These steps are what produced this page.

  

    

      

        
Build PX4 v1.17 SITL
git clone --recursive --branch v1.17.0 https://github.com/PX4/PX4-Autopilot.git
cd PX4-Autopilot && bash Tools/setup/ubuntu.sh   # installs Gazebo Harmonic too
make px4_sitl_default

        
Install the pacer
cd trackpace-sim
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt     # mavsdk, pyulog, numpy, pytest
pytest -q                           # 51 tests: geometry, staggers, schedule

        
Start a simulator
# Gazebo Harmonic, x500, the 400 m track world (add --gui to watch)
scripts/sitl_gz.sh ~/PX4-Autopilot
# or PX4's built-in SIH quadcopter, no Gazebo needed
scripts/sitl_sih.sh ~/PX4-Autopilot

        
Fly, then score from the log
python -m trackpace.fly config/gazebo_59.toml --out runs/gz59 \
    --ulog-dir ~/PX4-Autopilot/build/px4_sitl_default/rootfs/log
python -m trackpace.analyze runs/gz59        # laps, gap, path, repeatability
python -m trackpace.identify runs/gz59/flight.ulg   # drag for the config

Measured
All flights ran in real time on PX4 v1.17.0 SITL with default PX4 parameters, except EKF2_GPS_DELAY = 0 for the final Gazebo run (finding 4). The simulators were the built-in SIH quadcopter and Gazebo Harmonic 8.10 with the x500. Positions come from each simulator's ground truth in the PX4 log. Times come from the autopilot clock. Track geometry: 36.50 m kerb radius, 84.39 m straights, lane 1 measured 0.30 m outside the kerb. The tests check the World Athletics 400 m staggers to the centimetre.

    
Not measured
A real drone, wind, real GPS (non-RTK error is often 1–2 m, larger than the errors here), and people near the drone. The simulators' sensor noise is lighter than real hardware. The planner's tilt check uses a linear drag model. Figures are from single runs of 1–5 laps, not a statistical campaign.
